\section{TrustAuditFlow Design}

\subsection{Relationship with the BLoP Full-Node Mode}

TrustAuditFlow is a lightweight extension of the BLoP full-node trusted audit mode. BLoP provides the trusted node set, event monitoring, trusted execution support, and PBFT-style confirmation process. TrustAuditFlow keeps this mode as the high-assurance baseline and adds a risk-aware execution policy: high-risk events, disputed events, and critical state transitions are confirmed by the full trusted node set, while routine and batchable events are confirmed by a trusted audit committee.

This relationship is important for the paper's scope. TrustAuditFlow is not a weaker substitute for BLoP. It is an additional path for events whose risk and frequency make full-node confirmation expensive relative to the value of each individual event.

\subsection{Workflow}

Figure~\ref{fig:workflow} shows the closed audit-recovery workflow. The data object is first sharded and erasure-coded. The system then computes shard hashes, builds a Merkle root, and anchors the object commitment on chain. Auditors sample off-chain shards according to the policy. If a challenged shard is missing, stale, or inconsistent with its commitment, the system records an anomaly and checks whether enough valid shards remain for recovery. If recovery succeeds, the object commitment and the responsible node state are updated. If recovery is impossible or the event is high risk, the event falls back to full-node confirmation or external arbitration.

\subsection{Trust Score and Committee Selection}

BLoP maintains a trusted node set through trusted computing and monitoring. TrustAuditFlow reuses this idea and converts it into a committee-selection rule. In the current prototype-level design, the trust score of node $v_i$ is modeled as
\begin{equation}
  T_i = \alpha A_i + \beta C_i + \gamma P_i,
\end{equation}
where $A_i$ represents attestation or configuration status, $C_i$ represents historical audit behavior and credit events, and $P_i$ represents resource availability. The weights satisfy $\alpha+\beta+\gamma=1$.

Nodes below a threshold $\theta$ are excluded from the candidate set $V_T$. For a data object with policy $policy_D$, the system selects a committee $C \subseteq V_T$ according to risk level, audit frequency, and fault tolerance. If the committee tolerates $f$ Byzantine nodes, the number of available voting nodes must satisfy
\begin{equation}
  |C_{avail}| \geq 2f+1.
\end{equation}
If this condition fails, or if the object is marked high risk, the event is not processed by the lightweight path and is instead escalated to full-node confirmation.

\subsection{Risk-Aware Batch Anchoring}

TrustAuditFlow distinguishes between routine events and high-risk events. Routine events are stored off chain as an ordered event list. For every batch of size $b$, the system builds a Merkle root and writes one anchor to the chain. High-risk events use smaller batches, immediate anchoring, or full-node fallback.

For $n$ routine events and batch size $b$, the number of routine chain records becomes
\begin{equation}
  N_{chain} = \left\lceil \frac{n}{b} \right\rceil + N_{high},
\end{equation}
where $N_{high}$ is the number of high-risk events requiring separate handling. The goal is not to hide evidence, but to move detailed evidence off chain while preserving a verifiable on-chain digest.

\subsection{Sampled Audit and Anomaly Generation}

Given an audit policy, an auditor samples a challenge set $Q=\{q_1,\ldots,q_r\}$. For each challenged shard $s_i$, the storage node returns the shard, a digest, or a proof object depending on the verification module. In the current design, hash checking is used as a placeholder for the integrity check. A later revision can replace it with PDP/PoR verification.

If verification fails, the auditor emits an anomaly event
\begin{equation}
  e = \langle id_D, i, v_i, type, t, proof \rangle,
\end{equation}
where $type$ denotes missing shard, hash mismatch, timeout, stale response, or incomplete evidence. The event is appended to the off-chain hash chain and included in the next anchoring decision.

\subsection{Erasure-Code Recovery and Trust Update}

When an anomaly set $F$ is detected, the system checks whether the remaining valid shards satisfy the recovery threshold. For a $(k,m)$ erasure-code configuration, the object is recoverable if at least $k$ valid shards remain. If recovery succeeds, the system regenerates the damaged shard, recomputes the affected shard hashes, and updates the Merkle root. If recovery fails, the event is marked unrecoverable and escalated.

After recovery or failure, the responsible node trust score is updated:
\begin{equation}
  T_i' = T_i - \lambda_1 I_{damage} - \lambda_2 I_{timeout} + \lambda_3 I_{recovered}.
\end{equation}
Here $I_{damage}$, $I_{timeout}$, and $I_{recovered}$ represent damage, timeout, and successful recovery assistance events. This update closes the governance loop: audit outcomes influence later committee selection.

\subsection{On-Chain Confirmation}

Each audit batch generates an on-chain payload containing the audit summary, anomaly summary, recovery state, affected nodes, old Merkle root, new Merkle root, and off-chain evidence hash. Committee nodes vote on the payload under a PBFT-style quorum rule. A committed payload updates the object state and the node state. If the committee cannot satisfy quorum or if the event policy requires stronger assurance, the payload is sent to the full-node path.
