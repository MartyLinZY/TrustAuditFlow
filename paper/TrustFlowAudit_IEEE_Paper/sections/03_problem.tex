\section{Problem Formulation and Design Goals}

\subsection{BLoP Baseline and Extension Target}

This paper uses BLoP as the baseline trusted audit model. BLoP provides a full trust chain through trusted computing, trusted agents, event monitoring, and PBFT-style confirmation. Its natural operating mode is full-node confirmation: all eligible trusted nodes participate in confirming critical audit events. This is an appropriate default for high-risk data use, strong accountability requirements, and low-frequency events where assurance matters more than cost.

The extension target is different. In data circulation, routine audit events may be generated continuously by data connectors, storage nodes, computation tasks, and monitoring agents. If all routine events are handled by the same full-node path, the chain records and confirmation messages may grow faster than the value of the individual events. The research question is therefore:

\begin{quote}
Can a BLoP-style trusted audit system support a lightweight, risk-aware path for routine events while preserving full-node confirmation for high-risk or disputed events?
\end{quote}

\subsection{System Problem}

Consider a consortium data circulation scenario involving multiple organizations. A data owner registers a data object, splits it into shards, and stores the shards or computation evidence at off-chain nodes. Auditors periodically challenge selected shards or evidence objects. A consortium chain records commitments, audit summaries, recovery events, and trust-score updates. The system should verify data or evidence integrity without exposing plaintext data or committing bulky evidence to the chain.

The problem addressed by TrustAuditFlow is to design a low-on-chain-cost verification mechanism that can detect corrupted or missing off-chain evidence, trigger recovery when possible, record responsibility, and update future node selection. The mechanism must also make clear when lightweight committee confirmation is sufficient and when full-node confirmation is required.

\subsection{Threat Model}

We assume a permissioned setting in which participating organizations and nodes are registered, but some nodes may be faulty or Byzantine. Off-chain storage nodes may delete shards, return stale data, delay responses, or submit inconsistent evidence. Audit nodes may omit scheduled audits, misreport audit states, or collude with storage nodes. The consortium chain tolerates up to $f$ Byzantine nodes under a PBFT-style assumption. A committee confirmation is accepted only when the available voting nodes satisfy the required quorum.

The current design does not address broken cryptographic primitives, a committee fully controlled by an adaptive adversary, hardware side-channel attacks against TEEs, or business semantic fraud in the upstream data generation process. These limitations are deliberate: the paper focuses on the audit-flow and evidence-governance layer rather than claiming end-to-end semantic correctness.

\subsection{Design Goals}

TrustAuditFlow is designed around six goals.

\begin{itemize}
  \item \textbf{Low on-chain cost.} The chain stores commitments, Merkle roots, audit states, recovery states, and trust updates, not raw data or large proofs.
  \item \textbf{Traceable process.} Audit requests, anomaly detection, recovery actions, and node penalties must be anchored in a tamper-evident timeline.
  \item \textbf{Recovery closure.} When the number of damaged shards is within the erasure-code recovery threshold, an audit failure should trigger recovery and commitment update instead of only returning failure.
  \item \textbf{Lightweight committee confirmation.} A trust-score-driven committee confirms routine events as an optional path above the BLoP trusted node set.
  \item \textbf{Full-node fallback.} High-risk objects, insufficient committee trust, or disputed audit events fall back to BLoP-style full-node confirmation.
  \item \textbf{Explicit evidence boundary.} TrustAuditFlow does not replace BLoP's trusted computing layer or PDP/PoR cryptographic protocols; it organizes how those components can be anchored, confirmed, and linked to recovery.
\end{itemize}
