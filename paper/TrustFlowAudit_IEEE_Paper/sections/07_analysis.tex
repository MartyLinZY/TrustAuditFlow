\section{Security and Cost Analysis}

\subsection{Tamper Evidence and Traceability}

TrustAuditFlow uses two hash structures for traceability. First, shard hashes form a Merkle root. Once the root is anchored on chain, any later modification of a shard changes the corresponding leaf and invalidates the Merkle path. Second, audit events are ordered by a hash chain. If an attacker deletes, inserts, or modifies off-chain events after an anchor is committed, the recomputed hash-chain state will not match the anchored state.

This does not make off-chain evidence magically available. The evidence store must still preserve the raw audit materials. The contribution here is that the chain can detect inconsistency between the preserved evidence and the committed timeline.

\subsection{Committee Safety Boundary}

The committee path reduces routine confirmation cost, but it also introduces selection risk. If an adversary controls a committee majority for a target object, the committee could delay or approve a false audit summary. TrustAuditFlow handles this risk by using the committee only as a lightweight path: committee candidates must pass the trust threshold, committee membership should be rotated, high-risk events use larger committees or full-node confirmation, and any quorum failure triggers fallback.

Therefore, the security claim is limited. TrustAuditFlow does not claim that a small committee is as strong as the full BLoP trusted node set. It claims that the committee is a configurable optimization for routine events under explicit fallback rules.

\subsection{On-Chain Cost}

The on-chain cost comes from payload count, payload size, and consensus confirmation. Batch anchoring reduces the number of records for routine events. Committee confirmation reduces the number of voting nodes for routine events. Erasure coding reduces the redundancy needed to preserve recoverable evidence compared with naive replication.

These statements are design-level expectations, not empirical claims. The final paper still needs a controlled evaluation comparing at least four strategies: BLoP-style full-node PBFT, full-node PBFT with Merkle batch anchoring, committee confirmation without recovery closure, and TrustAuditFlow with committee confirmation plus recovery closure.

\subsection{Relation to PDP and PoR}

TrustAuditFlow does not replace PDP or PoR. PDP/PoR protocols prove possession or retrievability; TrustAuditFlow organizes how the challenge policy, proof summary, anomaly state, recovery result, and accountability record are anchored and confirmed. The current prototype-level hash check is useful for workflow validation, but a stronger paper version should replace it with public PDP/PoR verification or a zero-knowledge proof module.
